# Подботы — универсальный бот записи на приём в MAX

Один бот на всех. Каждый, кто его открыл в MAX, получает собственную
админ-панель, создаёт сколько угодно страниц записи («подботов») и
раздаёт клиентам ссылку. Клиент открывает ссылку, выбирает день и
время, заполняет форму — и записан. Регистрации нет: панель доступна
каждому, кто открыл бота.

Запись мгновенная, без подтверждения мастером. Мастер узнаёт о ней
сообщением сразу, клиент — подтверждением, а за сутки до визита ещё и
напоминанием.

---

## 1. Назначение решения

Частный мастер — маникюр, брови, парикмахер, репетитор, психолог,
автомастер — ведёт запись в мессенджере вручную: переписка, «а вы в
среду не заняты?», путаница во времени, забытые записи. На каждую
услугу нужен отдельный бот, а их не сделать без разработчика.

«Подботы» снимают это: владелец сам настраивает страницу записи в
админ-панели бота и получает ссылку. Расписание, перерывы, длительность
встречи, набор полей, горизонт записи, напоминания и утренняя сводка —
всё настраивается кнопками, без кода и без внешних сервисов.

Кому полезно:

| Кто | Что получает |
|---|---|
| Частный мастер | Свою страницу записи и список клиентов без админки и сайта |
| Клиент | Запись в три нажатия, без звонков и переписки |
| Небольшой кабинет | До 5 подботов на человека без регистрации и оплаты |

## 2. Основной пользовательский сценарий

**Владелец** (один раз настраивает):

```
/start → «Админ-панель» → «➕ Создать подбот» → ввести название
       → «Расписание» → задать интервал, например 10:00–18:00
       → «Записи» → скопировать ссылку и разослать клиентам
```

**Клиент** (основной сценарий, ради него всё и делалось):

```
открыть ссылку  →  выбрать день  →  выбрать время
                →  заполнить форму  →  подтвердить
                →  «Вы записаны»
```

Дальше автоматически: владельцу приходит карточка новой записи с
кнопкой отмены, клиенту — напоминание за 24 часа, владельцу в 09:00 по
часовому поясу подбота — сводка на день.

Клиент может в любой момент открыть «Мои записи», посмотреть или
отменить запись — отмена доступна не позже, чем за `cancel_notice_hours`
до визита.

## 3. Состав и архитектура

Один процесс, одна база данных SQLite, никаких других компонентов.

```
bot/
  domain/       чистая логика, без БД и без API MAX
    slots.py      нарезка расписания на слоты
    timeutil.py   часовые пояса, форматирование, полночь
    phone.py      нормализация и проверка телефона
    slug.py       транслитерация названия в адрес ссылки
    callback.py   коды кнопок (MAX ограничивает payload 40 символами)
    deeplink.py   разбор и сборка ссылок https://max.ru/<bot>?start=...
    models.py     Subbot, Booking, FormField, Interval
  db/           соединение и репозитории; весь SQL здесь
    connection.py   aiosqlite, WAL, foreign_keys, BEGIN IMMEDIATE
    migrations/     001_init.sql — вся схема
    repositories/   users, subbots, bookings, sessions, jobs
  services/     прикладные операции
    booking.py      слоты, бронирование, проверка полей формы
    notifier.py     все сообщения, которые бот шлёт сам
    scheduler.py    напоминания, дайджесты, уборка
    max_sender.py   отправка в MAX с ограничением 25 запросов в секунду
    ui.py           клавиатуры maxapi в одном месте
    text.py         все тексты в одном месте
  handlers/     сценарии
    client/         booking.py (запись), my_bookings.py (мои записи)
    admin/          панель, расписание, поля, правила, записи
  app.py        сборка зависимостей и Long Polling
tests/          254 теста
```

Правила разделения, которые держат проект под контролем:

- `domain/` ничего не знает о базе и о MAX — его можно тестировать без сети;
- весь SQL живёт в `db/repositories/`, поэтому переезд на PostgreSQL
  не затрагивает ни домен, ни обработчики;
- весь текст для пользователя — в `services/text.py`, вся клавиатура —
  в `services/ui.py`;
- состояние диалога — в таблице `sessions`, а не в памяти процесса:
  перезапуск контейнера посреди ввода данных не обнуляет его.

### Ключевые решения

**Слоты не хранятся.** Они считаются на лету как
`интервалы − перерывы − занятые записи`. Нарезка идёт от начала
интервала, неполный хвост отбрасывается, занятость определяется
пересечением интервалов, а не сравнением строк времени. Перерыв,
задевающий слот, вырезает слот целиком.

**Создание записи — в транзакции `BEGIN IMMEDIATE`.** Два клиента,
одновременно жмущие один слот, не смогут занять его оба: второй
получит «это время уже занято».

**Фоновые задачи — в таблице `jobs`, а не в таймерах.** Перезапуск
контейнера не теряет напоминание. Ключ дедупликации не даёт поставить
задачу дважды, неудачная попытка повторяется с паузой до трёх раз.

**Диалог хранится в БД, а не в памяти.** maxapi без FSM обходится
собственной таблицей `sessions`.

## 4. Запуск одной командой

```bash
cp .env.example .env    # вписать MAX_BOT_TOKEN и BOT_USERNAME
docker compose up -d --build
```

Это всё. Одна команда поднимает весь состав решения: сборка образа,
старт контейнера, создание базы, применение миграций, запуск
планировщика и подключение к MAX. Никаких других локальных компонентов
нет — ни базы, ни фронтенда, ни веб-сервера.

Проверить, что бот поднялся:

```bash
docker compose ps                        # статус
docker compose logs -f                   # логи в реальном времени
docker compose exec bot pytest -q        # 254 теста внутри контейнера
```

## 5. Необходимые параметры окружения

Обязательны два значения, без них бот не запустится и скажет об этом
одной строкой:

| Параметр | Что это | Где взять |
|---|---|---|
| `MAX_BOT_TOKEN` | Токен бота | Консоль MAX: <https://dev.max.ru>, создать бота |
| `BOT_USERNAME` | Никнейм бота без `@` | Там же, на странице бота |

Остальные значения имеют рабочие умолчания — см. `.env.example`, там
же комментарий к каждому.

## 6. Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `MAX_BOT_TOKEN` | — | Токен бота. Обязателен |
| `BOT_USERNAME` | — | Никнейм без `@`, из него собираются ссылки. Обязателен |
| `DEFAULT_TIMEZONE` | `Europe/Moscow` | Часовой пояс новых подботов |
| `MAX_SUBBOTS_PER_USER` | `5` | Сколько подботов может завести один человек |
| `MAX_SUBBOTS_PER_DAY` | `10` | Сколько подботов можно завести в сутки |
| `API_RATE_LIMIT` | `25` | Отправка, запросов в секунду (у MAX лимит 30) |
| `JOBS_POLL_INTERVAL` | `15` | Как часто планировщик проверяет очередь, секунды |
| `LOG_LEVEL` | `INFO` | `DEBUG` / `INFO` / `WARNING` / `ERROR` |
| `DATABASE_PATH` | `data/bot.db` | Файл SQLite; compose переопределяет на `/app/data/bot.db` |
| `TZ` | `Europe/Moscow` | Часовой пояс контейнера, не влияет на расписания подботов |

## 7. Используемые порты

**Ни одного.** Бот работает через Long Polling: он сам ходит к
`platform-api2.max.ru` и держит соединение наружу. Входящих соединений
нет, поэтому пробрасывать и открывать порты не нужно — в
`docker-compose.yml` секции `ports` нет намеренно.

Для диагностики — только Docker и логи:

```bash
docker compose ps
docker compose logs -f
```

## 8. Зависимости

**Язык и база:** Python 3.11+, SQLite (входит в `python:3.11-slim`),
часовые пояса IANA из пакета `tzdata`.

Прямые зависимости — `requirements.txt`, версии зафиксированы:

| Пакет | Версия | Зачем |
|---|---|---|
| `maxapi` | `1.2.2` | Клиент API MAX: поллинг, отправка, разбор событий |
| `aiosqlite` | `0.22.1` | Асинхронный SQLite: `sqlite3` синхронный и блокировал бы event loop |
| `pydantic-settings` | `2.15.0` | Чтение `.env` и переменных окружения |
| `tzdata` | `2026.4` | База IANA для `ZoneInfo` |

Транзитивные зависимости зафиксированы в `requirements-lock.txt`.
Инструменты разработки — в `requirements-dev.txt`
(`pytest 9.1.1`, `pytest-asyncio 1.4.0`, `ruff 0.16.9`).

MAX публикует форк `max-messenger/max-botapi-python`. Он не привязан к
версии и тянет за собой `git` при сборке, поэтому в зафиксированную
сборку не включён: используется `maxapi 1.2.2` с PyPI — версия, на
которой бот проверен сквозным прогоном против боевого MAX. Переключиться
на форк, если понадобится:

```bash
pip install "maxapi @ git+https://github.com/max-messenger/max-botapi-python.git@<коммит>"
```

## 9. Внешние сервисы и интеграции

Один внешний сервис, и он обязателен.

| Сервис | Назначение | Условия проверки |
|---|---|---|
| **MAX messenger** | Среда, в которой работает бот. API: `https://platform-api2.max.ru` | Рабочий `MAX_BOT_TOKEN` и `BOT_USERNAME` выданного бота. Воспроизвести внутри Docker нельзя: это платформа, а не компонент решения |
| IANA tz database | Часовые пояса для расписаний | Уже в составе образа, отдельно не нужен |

Что бот делает на стороне MAX:

- **Long Polling** забирает события: `/start`, сообщения, нажатия кнопок;
- **Отправляет сообщения** владельцу и клиенту;
- **Создаёт deep link** вида `https://max.ru/<bot>?start=s_<slug>` —
  механизм платформы, по которому клиент попадает на нужный подбот.

Своего API у решения нет: бот не поднимает HTTP-сервис и не отдаёт
данных наружу. Раздел требований «Только для решений с собственным API»
к нему не относится — см. `answer/DATA-API.yaml`.

## 10. Работа с данными

Всё хранится в одном файле SQLite, по умолчанию `data/bot.db`
(в контейнере `/app/data/bot.db` на именованном томе `botdata`).

| Таблица | Что хранит |
|---|---|
| `users` | Пользователь MAX: время последнего захода, сколько подботов создал за сутки |
| `subbots` | Подбот: название, slug, описание, часовой пояс, длительность слота, горизонт, лимиты отмены и напоминаний, час сводки |
| `workdays` | Дни недели, в которые подбот работает |
| `intervals` | Рабочие интервалы по дням недели, минуты от полуночи |
| `breaks` | Перерывы: вырезают слоты из рабочего времени |
| `form_fields` | Поля формы: тип, подпись, обязательность, порядок, длина |
| `bookings` | Записи: подбот, клиент, начало, конец, часовой пояс, статус |
| `booking_values` | Значения полей формы по каждой записи |
| `sessions` | Незавершённый диалог: кто что вводит прямо сейчас |
| `jobs` | Очередь фоновых задач: напоминания и дайджесты |
| `bot_state` | Служебное: маркер обновлений MAX для продолжения с прошлого места |

Правила целостности:

- включены `foreign_keys` и журнал WAL, `busy_timeout` — 5 секунд;
- создание записи идёт в `BEGIN IMMEDIATE`, двойная бронь невозможна;
- удаление подбота каскадно уносит его расписание, поля и записи;
- время везде хранится как unix-секунды UTC, а «какие сейчас сутки»
  считается в часовом поясе подбота — поэтому подбот в Екатеринбурге
  и подбот в Калининграде видят разное «сегодня» в один момент времени.

### Персональные данные

Телефон, имя, фамилия и комментарий клиента хранятся как присланы, без
нормализации и обезличивания, и удаляются вместе с записью. Данные не
уходят третьим лицам: единственный получатель — API MAX, через который
бот пишет самому клиенту. Резервных копий и аналитики нет.

## 11. Порядок работы с тестовыми данными

Тестовые данные **не нужны и не требуются**: бот начинает работать на
пустой базе.

Порядок такой:

1. **Ничего не готовить заранее.** Файл `bot.db` создаётся и
   мигрируется сам при первом старте. Пустая база — это валидное
   состояние: подботов нет, панель показывает приглашение создать
   первый.
2. **Создать подбот в интерфейсе.** Владелец открывает панель и
   проходит мастер создания. Это и есть проверка: вручную созданный
   подбот становится тестовыми данными.
3. **Заполнить расписание.** Без интервалов подбот клиентам не
   показывается ни одного дня — это видно сразу и служит проверкой, что
   расписание действительно участвует в выдаче слотов.
4. **Создать запись как клиент.** Открыть ссылку подбота (можно из
   того же аккаунта — владелец имеет право записаться сам), выбрать
   день, время, заполнить форму.
5. **Проверить уведомления.** Карточка записи у владельца, подтверждение
   у клиента, отмена из любой из двух точек.

Фикстур для отдельного прогона тестов тоже нет: 254 теста создают
подботы и записи сами, каждый в своей временной базе.

## 13. Примеры ожидаемого поведения

**Владелец создаёт подбот.** Кнопки меняют экраны, состояние диалога
сохраняется в БД. Если бросить ввод на сутки, сессия вычищается и
следующий `/start` начинает с чистого листа.

**Два клиента жмут один слот.** Первый получает подтверждение, второй —
«Это время уже занято, выберите другое». Проверено тестом
`test_booking_flow.py::test_double_booking_is_refused`.

**Клиент отменяет позже, чем `cancel_notice_hours`.** Бот отвечает, что
отменять поздно, до визита меньше двух часов. Владелец в это же время
отменить может — лимит по времени существует только для клиента.

**Перерыв задевает слот.** Интервал 10:00–18:00, перерыв 13:00–14:00,
длительность 60 минут: слот 13:00–14:00 исчезает целиком. Половинного
слота не бывает.

**Запись позже горизонта.** Кнопки дней заканчиваются через
`horizon_days`; нажать на «вчерашний» день бот не даёт.

**Бот перезапущен.** Напоминания и дайджесты не теряются: они лежат в
таблице `jobs`. Маркер обновлений MAX сохраняется каждые 5 секунд, и
после перезапуска бот не переигрывает старые нажатия.

**Нет сети.** Отправка не бросает исключений: она ограничивает скорость
25 запросов в секунду, повторяет попытку и возвращает `False`. Неудачная
фоновая задача повторяется три раза, а не теряется.

## 14. Известные ограничения

| Ограничение | Следствие | Почему так |
|---|---|---|
| **Панель открыта каждому** | Любой может создать подбот и писать от имени бота | Регистрации нет: мастер открыл бота — сразу работает. Смягчено лимитами `MAX_SUBBOTS_PER_USER` / `MAX_SUBBOTS_PER_DAY` и тем, что подбот без расписания клиентам не виден. PIN добавляется в `bot/handlers/admin/` без правок в `domain/` и `db/` |
| **Только Long Polling** | Нельзя запустить две копии с одной базой | Webhook требует публичного HTTPS и домена. Смена режима — это подключение Webhook в `bot/app.py` вместо `start_polling` |
| **SQLite** | Горизонтальное масштабирование невозможно | Весь SQL в `db/repositories/`, переезд на PostgreSQL не затрагиет остальное |
| **Без веб-морды** | Владелец работает только из MAX | Такова постановка: продукт живёт в мессенджере |
| **Напоминание не отправляется** | Если запись ближе, чем `reminder_hours` | Отправлять «завтра» вчера бессмысленно; запись в тот же день подтверждается сразу |
| **Нет возврата оплаты** | Предоплата не поддержана | Вне объёма MVP |

## 15. Остановка и повторный запуск

**Остановить:**

```bash
docker compose stop          # мягкая остановка, данные сохранены
docker compose down          # остановка и удаление контейнера, том остаётся
docker compose down -v       # то же плюс удаление тома с базой — необратимо
```

**Запустить снова:**

```bash
docker compose up -d --build
```

База лежит на именованном томе `botdata` и переживает остановку,
перезапуск и пересборку образа. `down -v` удаляет её вместе с записями.

**Локально, без Docker:**

```bash
# остановить: Ctrl+C в терминале
python -m bot
```

Ctrl+C и `SIGTERM` от Docker останавливают бота штатно: дописывается
маркер обновлений, гасится планировщик, закрываются соединения.

**Полностью с нуля:**

```bash
docker compose down -v && rm -f .env && cp .env.example .env
```

## Разработка и проверка качества

```bash
pip install -r requirements-dev.txt
pytest tests -q                # 254 теста
ruff check bot tests           # 0 замечаний
ruff format --check bot tests  # 0 замечаний
```

Тесты гоняют настоящий `Dispatcher` с настоящей SQLite: события MAX
собираются руками, отправка записывается подменным отправителем. Так
тест ловит и ошибки разбора кодов кнопок, и ошибки порядка регистрации
обработчиков — ровно то, что ломается в бою.

Часть правил линтера отключена осознанно, с пояснением в
`pyproject.toml`: `RUF001-003` (кириллица в русских строках и
типографское тире — не опечатка) и `D102`, `D103`, `D105`, `D107`
(docstring на каждой короткой обёртке над SQL только разбавляет те,
что действительно что-то поясняют). Остальное, включая аннотации типов
и `BLE`, проверяется строго.

## Данные и конфигурация

- `.env.example` — шаблон переменных **без** рабочих значений.
- `.env` — живой файл с токеном, в `.gitignore` и `.dockerignore`,
  в образ не попадает.
- `data/` — база SQLite, тоже игнорируется.
